# امنیت داده — دیپلوی کد ≠ پاک شدن داده

## اصل
هیچ داده‌ی کاربری داخل کد یا فایل‌های پروژه نیست. کاربران، رلیک، دفتر کل، پروفایل‌ها، پست‌ها، استوری‌ها، هدیه‌ها، تنظیمات (قیمت هدیه‌ها، هدیه‌های سفارشی، متن‌ها و …) همه در **MongoDB** هستند. دیپلوی دوباره‌ی کد (Vercel، git push، آپلود zip جدید) فقط کد را عوض می‌کند و به دیتابیس دست نمی‌زند. اسکیمای هیچ نسخه‌ای رکورد قدیمی را پاک نمی‌کند؛ مجموعه‌ها و ایندکس‌های جدید به‌صورت lazy ساخته می‌شوند و فیلدهای جدید برای رکوردهای قدیمی اختیاری‌اند (مثلاً هدیه‌ی قدیمی بدون `pub` موقع نمایش یکی می‌گیرد).

## تنها راه‌های واقعی از دست دادن داده
1. **عوض شدن `MONGODB_URI`** (کلاستر/کاربر دیگر) → ربات به دیتابیس دیگری وصل می‌شود و «خالی» به نظر می‌رسد. داده‌ی قبلی هنوز در کلاستر قبلی است؛ برگرداندن URI همه‌چیز را برمی‌گرداند.
2. **عوض شدن `MONGODB_DB_NAME`** (پیش‌فرض `nava`). اگر این env را اضافه/عوض کنی، ربات دیتابیس دیگری را می‌خواند. این env را **هیچ‌وقت** عوض نکن مگر عمداً.
3. **پاک کردن دستی** دیتابیس/کلکسیون در Atlas.
4. **کلاستر رایگان Atlas (M0) بدون بکاپ خودکار**: بکاپ پیوسته ندارد؛ بکاپ خودت را نگه دار (پایین).

## قبل از هر دیپلوی
- مطمئن شو env های `MONGODB_URI` و `MONGODB_DB_NAME` روی Vercel همان قبلی‌اند (دیپلوی عادی آن‌ها را عوض نمی‌کند، ولی «Project جدید» می‌سازد env خالی).
- یک بکاپ بگیر (پنل ادمین ← دسته‌ی داده‌ها ← «📤 خروجی اکسل کاربران»). همین فایل با «📥 ورودی اکسل (بازیابی)» قابل بازیابی است. توجه: این خروجی **کاربران** را پوشش می‌دهد، نه پست‌ها/هدیه‌ها/دفتر کل؛ برای بکاپ کامل از Atlas (Backup / `mongodump`) استفاده کن.
- اگر `BACKUP_CHANNEL_ID` تنظیم باشد بکاپ دوره‌ای به آن کانال می‌رود؛ تنظیم‌نبودنش باگ نیست.

## نسخه‌ی 1.17.0
فقط کلکسیون‌های جدید اضافه می‌کند: `mini_gift_defs`، `gift_events`، `gift_event_entries`، `post_reports` و چند ایندکس جدید روی `mini_gifts`. ایندکس یکتای هدیه‌ی یکتا فقط برای رکوردهای `uniqueGift:true` اعمال می‌شود، پس داده‌ی قبلی تداخلی ندارد. بازگشت به نسخه‌ی قبل (rollback کد) امن است؛ کلکسیون‌های جدید فقط بی‌استفاده می‌مانند.
